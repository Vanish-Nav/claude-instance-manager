# Launching instances and the taskbar

- There is no portable copy of Claude any more. Every isolated instance is started from the installed Claude Desktop itself: `<launch target> --user-data-dir=<profile path> --app-user-model-id=<profile AUMID>`. The MSIX app accepts these arguments through its App Execution Alias and runs a full separate instance while the official one keeps running.
- The launch target comes from `windows-claude-install.ts` (`ClaudeInstallResolver`), never from a hardcoded path:
  - `msix-direct`: package family `Claude_pzs8sxrjxfjjc`, alias `%LOCALAPPDATA%\Microsoft\WindowsApps\<family>\claude-desktop.exe`.
  - `msix-store`: package family `AnthropicPBC.Claude_fnn82j28hfe8t`, alias `claude-desktop-msstore.exe`.
  - `squirrel`: `%LOCALAPPDATA%\AnthropicClaude\app-*\claude.exe`, launched through the stub `%LOCALAPPDATA%\AnthropicClaude\claude.exe`; no package, no Start app id.
- Packages are found by family or publisher (`Get-AppxPackage | Where-Object { $families -contains $_.PackageFamilyName -or ($_.Publisher -like '*Anthropic*' ...) }`). Never filter by `-Name 'Claude*'`, `WindowsApps\Claude_*` or `AppID -like 'Claude_*'`: those masks only match the direct MSIX package.
- A running `Claude.exe` belongs to an install when its path starts with `<WindowsApps>\<Name>_` and contains `__<publisherId>\` (the parts that survive a package update), or lies under `AnthropicClaude\` for Squirrel. The primary instance is such a process whose command line has no `--user-data-dir`; an isolated instance is any process whose command line contains the profile path. Renderer processes (`--type=`) are ignored.
- With several installs, the resolver prefers the running one, then the owner of the `claude:` protocol (`HKCR\claude\shell\open\command`), then direct MSIX, Store, Squirrel. The chosen kind is shown in the overview; the resolved install is cached for the session and re-read by the Refresh button. A failed PowerShell query is never cached as "no install".
- The primary Claude is started with `explorer.exe shell:AppsFolder\<family>!Claude` (packaged) or the Squirrel stub. With the deep-link router enabled it is started as a managed instance instead (see sign-in.md).
- `TaskbarHelper.exe` is spawned with `<pid> <aumid> <display name> <icon path> <relaunch command>` and keeps applying, every 1.5 s while the process lives, the `System.AppUserModel` properties of the instance's windows: RelaunchCommand (2), RelaunchIconResource (3), RelaunchDisplayNameResource (4), ID (5). Preserve the helper when changing launch or taskbar behaviour.
- **The window property store rejects a RelaunchCommand of 260 characters or more** (`0x8007007A`, measured: 252 accepted, 280 rejected). A direct launch command with the profile path and the AUMID is about 305 characters, so the relaunch command is `"<manager exe>" --launch-profile=<profile id>` (~145). The value must be joined with `=`: Chromium reorders the switches of a second instance before `second-instance` receives its argv, so a space-separated value lands behind an injected switch. The manager handles that argument on its first start (window stays hidden) and in `second-instance`, starts the instance and attaches the helper. A property the shell refuses is logged to stderr and skipped; it must never end the helper, otherwise the AUMID and icon are not applied either and every instance stacks under the Claude button.
- On every full state refresh the manager re-attaches a helper to a running isolated instance that has none (manager restarted, helper gone); helpers are recognised by the AUMID on their command line. A helper whose relaunch command points at another manager executable is restarted, and shortcuts and taskbar pins (`User Pinned\TaskBar`, `User Pinned\ImplicitAppShortcuts\<hash>`) that target another manager executable are repointed at this one. A development build (`win-unpacked`, or not packaged) never claims them.
- Renaming or recolouring an instance updates the icon and description of its taskbar pins; the pin label is the `.lnk` file name, which Windows references by path, so it cannot follow a rename (re-pin for a new label).
- Renaming an instance restarts its helper (the one known to this manager process, or any `TaskbarHelper.exe` whose command line carries the profile AUMID), otherwise the old helper keeps re-applying the old display name.
- The default colour uses the icon embedded in the real `Claude.exe` of the install (`iconSource`); it is readable by the user even under `WindowsApps`. Other colours use the packaged `Assets\claude-profile-<color>.ico`. Bump the AUMID version (`profile.v3`) when an icon resource changes: Windows caches taskbar icons by AUMID.
- **A packaged Claude.exe ignores `--app-user-model-id`**: the package identity wins, so an instance started directly (alias + `--user-data-dir`) stacks under the Claude button until TaskbarHelper sets the per-window properties. Profile shortcuts (`Claude — <name>.lnk`) therefore target the manager with `--launch-profile=<id>`, the colour icon and the profile AUMID, exactly like a pinned button; the manager starts hidden if it is not running. On start the manager rewrites, once, every shortcut that launches a profile directly (portable copy or alias) to that form, repoints a plain `Portable\Claude.exe` shortcut at the installed Claude, and offers to delete the `Portable` folder (`settings.json: portableCleanupDismissed`). Helpers are also re-attached on the 10 s poll, so an instance started by any other means gets its identity while the manager runs.
- **Manual check:** the pin click itself (a pinned button starting the instance after a reboot, and the pinned icon keeping its colour) must be verified by hand after each change to the helper or the shortcut details. Neither the unit tests nor the build exercise the Windows shell.
- Avoid custom WinAPI window activation where possible. A second launch with the same `--user-data-dir` lets Claude's ProcessSingleton show its own hidden tray window; TaskbarHelper `--activate` is the fallback.
- Closing an instance sends a plain `taskkill /PID … /T` first (WM_CLOSE, Claude can persist its state) and forces (`/F`) only after about six seconds of waiting.
- Other TaskbarHelper modes: `--singleton-title <pid…>` prints the title of the Chromium single-instance window (`Chrome_MessageWindow`, message-only) owned by one of the processes, which is that instance's data folder; `--relay` and `--router` are described in sign-in.md. The relay payload parser (`RelayPayload.cs`) has its own tests in `taskbar-helper/tests`, run by `npm test`.
